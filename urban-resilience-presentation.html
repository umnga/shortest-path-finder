01 · Why This Project

Two questions every road network has to answer

QUESTION 1

What's the fastest way from A to B — right now?

Kathmandu Valley traffic is dense and unevenly distributed. A driver, an ambulance, or a delivery route all need the same thing: the shortest path through a huge, sparse, real-world graph — computed fast enough to feel instant.

QUESTION 2

Which roads is the network quietly depending on?

Construction, floods, festivals, and accidents close roads constantly. Some closures barely matter. Others cut off entire neighborhoods. Which roads are those — before they close, not after?

UrbanResilience Analyzer answers both, on the same underlying graph: a Route Finder for question one, and an Edge Criticality & Vulnerability Engine for question two.

02 · From Roads to Graphs

The road network as a weighted graph

We pull Kathmandu's real, drivable street network using OSMnx. Every intersection becomes a node; every road segment between two intersections becomes an edge, weighted by distance.

WHY AN ADJACENCY LIST

A city road network is sparse — each intersection connects to a handful of others, not to every other intersection. An adjacency list stores exactly those real connections, giving O(V+E) space instead of the O(V²) an adjacency matrix would waste on mostly-empty entries.

adj[E] = [ {to: G, w: 8}, {to: H, w: 8}, {to: C, w: 9}, {to: B, w: 9}, {to: F, w: 8} ]
03 · Three Ways to Search the Same Graph

Dijkstra, A*, and Bidirectional Dijkstra

GREEDY · UNINFORMED

Dijkstra's Algorithm

Always expands the cheapest unvisited node next, using a binary min-heap. Guarantees the shortest path, exploring outward in every direction equally.

  • O((V+E) log V)
GREEDY · INFORMED

A* Search

Same relaxation step as Dijkstra, but a haversine-distance heuristic pulls expansion toward the destination — same guarantee, usually far fewer nodes touched.

  • O((V+E) log V) worst case
GREEDY · TWO-SIDED

Bidirectional Dijkstra

Runs Dijkstra from the source and from the destination at once, stopping the instant the two frontiers meet in the middle.

  • ≈ halves the search radius

All three return the same optimal path on a graph with non-negative weights — they differ only in how many nodes they have to touch to find it. That difference is exactly what the Route Finder measures.

06 · Empirical Benchmarks

Watching the complexity, not just stating it

Real map data has one graph size. To actually see O((V+E) log V) per search and O(E·(V+E) log V) for a full criticality sweep, the engine generates synthetic grid graphs of increasing size and times every pass.

PER RUN, THE SUITE REPORTS
  • Dijkstra runtime at each grid size
  • Full criticality-sweep runtime at each grid size
  • Bottleneck count found at each size

Illustrative growth shape — single search (teal) vs. full edge sweep (amber) as grid size increases.

08 · Syllabus Integration

Where each feature comes from the course

CH. 2 — GREEDY STRATEGIES

Dijkstra's greedy relaxation: always commit to the cheapest known distance, never revisit that choice.

GRAPH DATA STRUCTURES

Adjacency-list storage plus a binary min-heap priority queue for efficient extract-min.

HEURISTIC SEARCH

A* with an admissible haversine heuristic — informed search without losing optimality.

EMPIRICAL PERFORMANCE PROFILING

Measured, not assumed: O((V+E) log V) per search, O(E·(V+E) log V) for a full criticality sweep — confirmed against the synthetic-grid benchmark suite.
